# Заметки по проекту «Сыграем»

## 0. СЕЙЧАС: вход по номеру телефона с паролем
Вход через Google убран полностью — он так и не заработал (Supabase не мог
обменять код у Google), и Gmail в Казахстане мало кто использует. Провайдер
Google в Supabase выключен, OAuth-клиент в Google Cloud удалён, в коде слова
`google` больше нет.

Вместо него — номер телефона и пароль, без SMS. Как это устроено — п. 1,
от каких настроек Supabase зависит — п. 9.

**Что проверено** (5 окт 2026, запросами к настоящему Supabase):
- регистрация и вход проходят, `email_confirmed_at` заполняется сразу, без письма;
- `first_name` и `last_name` сохраняются в `user_metadata`, кириллица целая,
  на экране собирается «Арман Б.»;
- Supabase сам дописывает в метаданные `email`, `email_verified`,
  `phone_verified`, `sub` — поэтому свои поля названы иначе (п. 1);
- нормализация номера и тексты ошибок — тестами на заглушке вместо Supabase;
- `npm run lint` и `npm run build` проходят.

**Что НЕ проверено:** кликами в браузере. Не закоммичено.

## 1. Как устроен вход (и почему так)
**Phone + password в Supabase без SMS-провайдера невозможен.** Чтобы включить
провайдер Phone, он требует ключи Twilio или аналога. Люди вписывают туда
поддельные ключи и снимают подтверждение — это костыль, и он ломается на любой
функции, которая попытается отправить SMS. Отказались сознательно.

Поэтому **логином служит номер, превращённый в фиктивный email**:

```
+7 701 123 45 67  →  +77011234567  →  77011234567@phone.sygraem.kz
```

Письма туда не уходят: подтверждение почты выключено (п. 9), поэтому адрес —
просто строка-ключ аккаунта.

- `src/utils/phone.js` — `normalizePhone` приводит `+7 701…`, `8 701…` и
  `701…` к одному виду. Это главное требование схемы: из трёх способов набора
  должен получаться **один** логин, иначе человек вместо входа молча создаст
  себе второй аккаунт. 10 цифр без кода считаем казахстанскими. Мобильные
  префиксы нарочно не проверяем — операторы заводят новые диапазоны, и такая
  проверка начала бы отказывать живым людям.
- **Домен `phone.sygraem.kz` менять нельзя.** Другой домен → другой логин у
  всех → никто не войдёт. Пока живых пользователей нет, менять ещё можно;
  после первого — уже нет.
- `src/lib/auth.js` — `signUp`, `signIn`, `signOut`. Возвращают
  `{ ok, message }`, как `handleCancelGame`. Ошибки Supabase переводятся по
  `error.code` с запасным поиском кода внутри текста.
- Имя и фамилия хранятся **порознь** (`first_name`, `last_name`). Собрать
  «Арман Б.» из двух полей можно всегда, а разделить обратно — нет: «Али-Султан
  Абу Бакир», и граница не угадывается. Разделение делает один раз сам человек
  в форме.
- Ключи `email` и `phone` в `user_metadata` занимает сам Supabase, поэтому наши
  называются `contact_email` и `login_phone`. Проверено живым ответом сервера:
  настоящая почта в ключе `email` была бы перетёрта служебным адресом.
- Почта при регистрации необязательная, лежит в `contact_email` на будущее.
  **Восстановления пароля нет** и не будет без своего SMTP: Supabase отправляет
  письмо только на адрес аккаунта, а он фиктивный. Пока забытый пароль меняется
  вручную в дашборде. Поэтому в форме есть галочка «Показать пароль» — опечатка
  при регистрации иначе означает потерянный аккаунт.
- `displayName` в `src/utils/user.js` собирает «Арман Б.» и используется в трёх
  местах: шапка, поле «Твоё имя (организатор)», поле имени при записи. Два
  последних уходят в базу, то есть их видят все — одна функция гарантирует, что
  они не разойдутся. Запасной вариант `user.email` оттуда **убран**: там теперь
  служебный адрес, и он попал бы в список участников.
- `src/components/AuthForm.jsx` — одна форма на вход и регистрацию. Про Supabase
  не знает: собирает поля и получает обратно `{ ok, message }`.
- Кнопка «Войти» в шапке не входит, а прокручивает к форме — поэтому оформлена
  текстом со стрелкой «↓», как «Выйти» на том же месте, а заливка оставлена
  единственному настоящему действию: кнопке в форме.
- Сессия после F5 держится сама: `getSession()` + `onAuthStateChange` в
  `App.jsx`. Вход и регистрация нарочно **не** ставят пользователя сами — это
  делает `onAuthStateChange`, один путь на вход, обновление страницы и выход.

**Сторона базы не менялась вообще.** `auth.uid()` одинаковый при любом способе
входа, поэтому остались как были: колонка
`games.owner_id uuid references auth.users (id) on delete cascade`; политики
`games_select_all`, `games_insert_own`, `games_update_own`, `games_delete_own`;
функция `join_game(p_game_id bigint, p_name text)` и права на неё. SQL в эту
работу не писался ни строки.

Один тип аккаунта для всех — организатором становится тот, кто создал игру.
Отмена по секретному коду убрана давно; `cancel_game` лежит в базе без дела,
можно дропнуть.

## 2. Дальше по плану
Ближайшее: прокликать вход в браузере и закоммитить.

Потом на выбор: страница «мои игры»; запрет записываться на одну игру дважды;
деплой на sygraem.kz (тогда добавить домен в Supabase → URL Configuration —
Google Cloud больше не при чём).

Отдельной задачей — восстановление пароля: нужен свой SMTP (например Resend),
страница «введи новый пароль» и решение, что делать с теми, кто почту не
оставил. Тогда же можно включить «Prevent use of leaked passwords» — сейчас оно
выключено, потому что наш текст ошибки `weak_password` говорит про длину и
соврал бы.

Мелочь: ветка `meta.name` в `displayName` — страховка для аккаунтов, созданных
до разделения имени и фамилии. Таких аккаунтов не существует (регистрация тогда
вообще не работала, п. 8), ветку можно удалить.

## 3. Проверка защиты без браузера
Стучаться curl-ом публичным ключом из `.env` — так это видит посторонний:
- `GET /rest/v1/games` → 200 (читать можно всем);
- `POST /rest/v1/games` → `42501 new row violates row-level security policy`;
- `POST /rest/v1/rpc/join_game` → `permission denied for function`;
- `PATCH /rest/v1/games?id=eq.1` → `[]` и **HTTP 200**.

Последнее важно: на запрет база отвечает не ошибкой, а пустым списком.
Поэтому в коде удаления стоит `.select()` — иначе «ничего не удалилось»
выглядит как успех.

## 4. Урок: SQL Editor и `$$`
Supabase SQL Editor может влезть в тело функции, если разделитель —
голый `$$`. Всегда писать именованный: `$func$ ... $func$`. После
создания функции смотреть, что реально сохранилось:
`select prosrc from pg_proc where proname = '...'`.

## 5. Урок: права на функции
`revoke execute ... from public` **не убирает** доступ у `anon` — в
Supabase у этой роли свой отдельный грант. Для каждой новой функции:
```sql
revoke execute on function public.имя(типы) from public;
revoke execute on function public.имя(типы) from anon;
grant  execute on function public.имя(типы) to authenticated;
```
Проверять через `select proacl from pg_proc where proname = '...'`.

## 6. Урок: "Success" ничего не доказывает
Если несколько операторов идут одним запросом, ошибка в одном молча
откатывает остальные. Правило:
- выполнять по одному блоку за раз (таблица / функция / grant отдельно);
- после каждого — проверять факт через `information_schema.columns`
  (для колонок/таблиц) или `select proname from pg_proc where proname = '...'`
  (для функций), а не полагаться на текст "Success";
- после изменения схемы — `notify pgrst, 'reload schema';` (обязательно
  для таблиц/колонок/функций; для политик не требуется).

## 7. Прошедшие игры скрыты + урок про часовой пояс
Висящая наверху игра с прошлого четверга делала сайт мёртвым. Теперь в
списке только то, что ещё впереди. Строки в базе не трогаем — только
фильтруем при чтении.

Фильтр намеренно разрезан на две половины:
- **границу по дням — в запросе**: `.gte('date', todayIso())` в
  `loadGames`. Таблица растёт вечно, и качать весь архив в браузер,
  чтобы его выбросить, незачем;
- **время сегодняшних игр — в коде**: производный
  `upcomingGames = games.filter(isUpcoming)` в `App.jsx`, он и уходит в
  `GameList`.

**Урок (главное здесь): время нельзя сравнивать с `now()` на стороне
базы.** `now()` в Postgres — это UTC, а Алматы UTC+5. Пять часов в
сутках считались бы неверно: игра, которая по местным часам ещё
сегодня вечером, по UTC уже другой день. При этом подпись на карточке
(«Сегодня, 19:00») рисует `humanizeDate` по часам браузера. Значит и
решение «прошла или нет» должно приниматься теми же часами — иначе
список и подписи расходятся. Эти часы есть только в браузере, поэтому
сравнение времени живёт в коде, а не в SQL.

Побочный плюс: запрос — это снимок на момент загрузки, а `filter` на
рендере пересчитывается. Игра, начавшаяся при открытой странице,
уезжает из списка сама.

Чего этот фильтр **не** делает: это не защита. Прошедшие игры
по-прежнему отдаёт `GET /rest/v1/games` — политика `games_select_all`
их не скрывает. Для этих данных нормально, но не считать их спрятанными.

Вариант «всё одним запросом» —
`.or('date.gt.X,and(date.eq.X,time.gte.Y)')` — рассмотрен и отброшен:
тащит синтаксис PostgREST в строку, всё равно требует передать местное
время из браузера и ломается на часах, идущих во время сессии.

В `src/utils/date.js` добавлены `todayIso()` (местная дата в формате
колонки `games.date`), `gameStart()` и `isUpcoming(game, now)`. У
`isUpcoming` второй аргумент — чтобы проверять на фиксированном
«сейчас» без ожидания четверга.

Сортировка менять не потребовалась: `.order('date').order('time')` по
возрастанию уже даёт ближайшую игру первой, та же сортировка стоит на
вставке новой игры. Заодно `featured={index === 0}` в `GameList`
выделяет теперь действительно ближайшую, а не самую старую.

Пришлось закрыть побочное следствие: форма пускала прошедшую дату, и
игра создавалась бы, но тут же исчезала из списка — при экране «Игра
создана! Она уже в списке». Поэтому в `handleSubmit` проверка
`isUpcoming({ date, time })` перед вставкой и `min={todayIso()}` на
поле даты.

Проверено на фиксированном «сейчас» 2 окт 19:30: прошлый четверг —
скрыт, сегодня 18:00 — скрыт, сегодня 19:30 ровно — виден, сегодня
21:00 и завтра 08:00 — видны. Сборка и линт проходят. Кликами в
браузере не проверено, не закоммичено (лежит в той же рабочей копии,
что и работа по входу из п. 1).

## 8. Урок: ошибка говорит, где упало, а не почему
Регистрация падала с ответом Supabase:

```
HTTP 400
{"error_code":"email_address_invalid",
 "msg":"Email address \"77000000001@phone.sygraem.kz\" is invalid"}
```

Сообщение прямо указывало на домен, и логично было решить, что Supabase не
принимает `phone.sygraem.kz`. **Дело было не в домене.** Supabase проверяет
адрес на доставляемость только тогда, когда собирается отправить на него
письмо. Пока подтверждение почты было включено, он смотрел на домен, не находил
MX-записей и честно отвечал «адрес невалидный». Выключили подтверждение —
отправлять стало нечего, проверять тоже, и тот же самый домен заработал без
единой правки в коде.

Проверено после: `phone.sygraem.kz`, `example.com`, `phone.invalid` и
`sygraem.kz` — все четыре дают HTTP 200. То есть домен вообще не при чём.

**Вывод: сообщение об ошибке говорит, где упало, а не почему.** Если бы мы
сразу поменяли домен на `example.com`, регистрация всё равно падала бы — только
с другим текстом, и настоящая причина осталась бы ненайденной.

Это та же мысль, что в п. 6, с другой стороны: там «Success» ничего не
доказывал, здесь текст ошибки указывал не туда.

Поэтому в `AUTH_ERRORS` код `email_address_invalid` теперь ведёт к подсказке про
подтверждение почты, а не про домен. Туда же ведёт `over_email_send_rate_limit`:
этот код приходит, только если Supabase пытается отправлять письма, а их быть
не должно вовсе.

## 9. Настройки Supabase, от которых зависит вход
Тумблера **«Confirm email» в дашборде больше нет**. В Authentication → Sign In /
Providers → Email список идёт: Enable email provider → Secure email change →
Secure password change → Require current password → Prevent use of leaked
passwords → Minimum password length → Password requirements → Email OTP
expiration → Email OTP length. Между первым и вторым пунктом пусто. В
Authentication → Emails только шаблоны и SMTP, тумблеров нет.

Настройка живёт в **Management API**:

```
PATCH https://api.supabase.com/v1/projects/{ref}/config/auth
{"mailer_autoconfirm": true}
```

Поля: `mailer_autoconfirm` (true = подтверждение выключено, письма не нужны),
`external_google_enabled`, `disable_signup`. Токену нужны права
`auth_config_write` и `project_admin_write`.

Лучше отправлять по одному полю за запрос: PATCH применяется целиком, и если
одно поле не понравится серверу, не применится ничего (та же мысль, что в п. 6).

**Как посмотреть текущее состояние — без токена**, публичным ключом из `.env`:

```
GET /auth/v1/settings
```

Должно быть так:

| Поле | Значение |
|---|---|
| `mailer_autoconfirm` | `true` — иначе регистрация падает, см. п. 8 |
| `email` | `true` — вся схема держится на email-входе |
| `disable_signup` | `false` |
| `google` | `false` |
| `phone` | `false` — SMS-провайдер не задействован |

Если регистрация вдруг сломается — смотреть сюда первым делом, а не в код.

## 10. Урок: `curl` в PowerShell — это не curl
В Windows PowerShell 5.1 `curl` — псевдоним `Invoke-WebRequest`, и команда в
стиле curl падает с непонятной ошибкой. Нужен родной вызов:

```powershell
Invoke-RestMethod -Method Patch -Uri "https://api.supabase.com/v1/projects/{ref}/config/auth" `
  -Headers @{ Authorization = "Bearer $token" } `
  -ContentType "application/json" `
  -Body '{"mailer_autoconfirm": true}'
```

Тело — в **одинарных** кавычках, тогда PowerShell передаёт JSON как есть и не
толкует `{` и `"` по-своему.

Если ловишь «недопустимые знаки управления» — в токен попал перенос строки при
копировании. Лечится так:

```powershell
$token = "sbp_..."
$token = $token.Trim()
```

В Git Bash работает обычный `curl`, там этой подмены нет.

## 11. Личный токен Supabase — ключ ко всему аккаунту
Personal access token (`sbp_...`) даёт доступ **ко всем проектам аккаунта**, а не
к одному. Создавать на конкретную задачу, сразу после — удалять на
https://supabase.com/dashboard/account/tokens. В `.env` не кладём, в git не
коммитим, в переписку не вставляем.

Отдельно: ответ `GET /v1/projects/{ref}/config/auth` содержит `smtp_pass` и
`external_google_secret` в открытом виде. Этот вывод нельзя никуда копировать
целиком — только нужное поле.
