# Заметки по проекту «Сыграем»

## 0. СЕЙЧАС НЕ РАБОТАЕТ: вход через Google
При возврате с Google в адресе:
```
error=server_error
error_code=unexpected_failure
error_description=Unable to exchange external code
```
Это Supabase не смог обменять у Google код на токен. Ошибка приходит
от Supabase ещё до сайта — значит код проекта ни при чём, дело в
настройках OAuth.

Уже проверено и совпадает:
- redirect URI в Google = Callback URL в Supabase
  (`https://wdwuwhmfvnxghmpubyhl.supabase.co/auth/v1/callback`);
- Supabase → URL Configuration: Site URL и Redirect URLs на
  `http://localhost:5173`.

Главная гипотеза: **Client Secret в Supabase неверный или неполный** —
Google показывает его один раз при создании, мог скопироваться не
целиком (или с лишним пробелом/переносом в конце).

План на завтра:
1. Supabase → Logs → Auth, найти эту попытку входа и посмотреть, что
   именно ответил Google. Если там `invalid_client` — секрет точно
   виноват, дальше по пунктам ниже.
2. Google Cloud → Clients → создать **новый** OAuth-клиент, тип
   Web application.
3. Сразу из всплывающего окна скопировать **и** Client ID, **и** Secret
   (не с разных клиентов — это частая путаница после пересоздания).
4. Вписать оба в Supabase → Authentication → Sign In / Providers →
   Google, сохранить, проверить что провайдер остался включённым.
5. В новом клиенте заново прописать redirect URI (Callback URL из
   Supabase) и JavaScript origin `http://localhost:5173` — у нового
   клиента их нет, они не переносятся со старого.

## 1. Сделано, но не проверено вживую
Код входа через Google написан целиком, линт и сборка проходят, но
проверить вход кликом не удалось из-за ошибки выше. Сторона базы при
этом проверена и работает — см. п. 3. Не проверено только то, что
требует живого входа: сессия, `owner_id` у новой игры, кнопки для
владельца. Не закоммичено.

Один тип аккаунта для всех — организатором автоматически становится
тот, кто создал игру.

В базе:
- колонка `games.owner_id uuid references auth.users (id) on delete cascade`;
- старые политики (`read_games`, `insert_games`, `update_games`) удалены,
  вместо них `games_select_all` (читают все), `games_insert_own`,
  `games_update_own`, `games_delete_own` (всё по `auth.uid() = owner_id`);
- функция `join_game(p_game_id bigint, p_name text) returns games`,
  `security definer`, `set search_path = ''` — через неё идёт запись на
  игру, потому что напрямую `update` чужой игры политика не пускает.
  Внутри: проверка входа, проверка мест, `for update` против гонки за
  последнее место.

В коде: `AuthBar` (вход/выход), `owner_id` при создании, запись через
`supabase.rpc('join_game')`, удаление напрямую через `delete` — его
режет `games_delete_own`.

Отмена по секретному коду убрана: у каждой игры теперь есть владелец,
и он удаляет её кнопкой. `src/utils/cancelCode.js` удалён, функция
`cancel_game` в базе осталась лежать без дела — можно дропнуть.

## 3. Проверка защиты без браузера
Стучаться curl-ом публичным ключом из `.env` — так это видит посторонний:
- `GET /rest/v1/games` → 200 (читать можно всем);
- `POST /rest/v1/games` → `42501 new row violates row-level security policy`;
- `POST /rest/v1/rpc/join_game` → `permission denied for function`;
- `PATCH /rest/v1/games?id=eq.1` → `[]` и **HTTP 200**.

Последнее важно: на запрет база отвечает не ошибкой, а пустым списком.
Поэтому в коде удаления стоит `.select()` — иначе «ничего не удалилось»
выглядит как успех.

## 4. Урок: SQL Editor и `$$`
Supabase SQL Editor может влезть в тело функции, если разделитель —
голый `$$`. Всегда писать именованный: `$func$ ... $func$`. После
создания функции смотреть, что реально сохранилось:
`select prosrc from pg_proc where proname = '...'`.

## 5. Урок: права на функции
`revoke execute ... from public` **не убирает** доступ у `anon` — в
Supabase у этой роли свой отдельный грант. Для каждой новой функции:
```sql
revoke execute on function public.имя(типы) from public;
revoke execute on function public.имя(типы) from anon;
grant  execute on function public.имя(типы) to authenticated;
```
Проверять через `select proacl from pg_proc where proname = '...'`.

## 6. Урок: "Success" ничего не доказывает
Если несколько операторов идут одним запросом, ошибка в одном молча
откатывает остальные. Правило:
- выполнять по одному блоку за раз (таблица / функция / grant отдельно);
- после каждого — проверять факт через `information_schema.columns`
  (для колонок/таблиц) или `select proname from pg_proc where proname = '...'`
  (для функций), а не полагаться на текст "Success";
- после изменения схемы — `notify pgrst, 'reload schema';` (обязательно
  для таблиц/колонок/функций; для политик не требуется).

## 7. Прошедшие игры скрыты + урок про часовой пояс
Висящая наверху игра с прошлого четверга делала сайт мёртвым. Теперь в
списке только то, что ещё впереди. Строки в базе не трогаем — только
фильтруем при чтении.

Фильтр намеренно разрезан на две половины:
- **границу по дням — в запросе**: `.gte('date', todayIso())` в
  `loadGames`. Таблица растёт вечно, и качать весь архив в браузер,
  чтобы его выбросить, незачем;
- **время сегодняшних игр — в коде**: производный
  `upcomingGames = games.filter(isUpcoming)` в `App.jsx`, он и уходит в
  `GameList`.

**Урок (главное здесь): время нельзя сравнивать с `now()` на стороне
базы.** `now()` в Postgres — это UTC, а Алматы UTC+5. Пять часов в
сутках считались бы неверно: игра, которая по местным часам ещё
сегодня вечером, по UTC уже другой день. При этом подпись на карточке
(«Сегодня, 19:00») рисует `humanizeDate` по часам браузера. Значит и
решение «прошла или нет» должно приниматься теми же часами — иначе
список и подписи расходятся. Эти часы есть только в браузере, поэтому
сравнение времени живёт в коде, а не в SQL.

Побочный плюс: запрос — это снимок на момент загрузки, а `filter` на
рендере пересчитывается. Игра, начавшаяся при открытой странице,
уезжает из списка сама.

Чего этот фильтр **не** делает: это не защита. Прошедшие игры
по-прежнему отдаёт `GET /rest/v1/games` — политика `games_select_all`
их не скрывает. Для этих данных нормально, но не считать их спрятанными.

Вариант «всё одним запросом» —
`.or('date.gt.X,and(date.eq.X,time.gte.Y)')` — рассмотрен и отброшен:
тащит синтаксис PostgREST в строку, всё равно требует передать местное
время из браузера и ломается на часах, идущих во время сессии.

В `src/utils/date.js` добавлены `todayIso()` (местная дата в формате
колонки `games.date`), `gameStart()` и `isUpcoming(game, now)`. У
`isUpcoming` второй аргумент — чтобы проверять на фиксированном
«сейчас» без ожидания четверга.

Сортировка менять не потребовалась: `.order('date').order('time')` по
возрастанию уже даёт ближайшую игру первой, та же сортировка стоит на
вставке новой игры. Заодно `featured={index === 0}` в `GameList`
выделяет теперь действительно ближайшую, а не самую старую.

Пришлось закрыть побочное следствие: форма пускала прошедшую дату, и
игра создавалась бы, но тут же исчезала из списка — при экране «Игра
создана! Она уже в списке». Поэтому в `handleSubmit` проверка
`isUpcoming({ date, time })` перед вставкой и `min={todayIso()}` на
поле даты.

Проверено на фиксированном «сейчас» 2 окт 19:30: прошлый четверг —
скрыт, сегодня 18:00 — скрыт, сегодня 19:30 ровно — виден, сегодня
21:00 и завтра 08:00 — видны. Сборка и линт проходят. Кликами в
браузере не проверено, не закоммичено (лежит в той же рабочей копии,
что и работа по входу из п. 1).
